# 공개 AI 에이전트 스킬 1,800개를 검증해봤다

*2026-10-22 · Kwan Hyeon*

SKILL.md는 새 npm이다. 코딩 에이전트에 스킬 서른 개를 깔고 한 개도 안 읽어본다. 공개 스킬 1,831개를 가져와 린트하고, 프롬프트 인젝션 패턴을 스캔하고, 안에 든 지시 29,880개를 뽑아내서 서로 모순되는 게 없는지 확인했다. 세 가지가 나왔다. 다섯 중 하나만 라이선스를 밝힌다. 스킬 간 정면 충돌은 사실상 없다. 그리고 두 스킬이 갈릴 때 에이전트는 동전을 던지지 않는다. 조용히 한쪽을 고르고, 매번 같은 쪽을 고른다.

## 무엇을 했나

소스는 둘이다. Anthropic의 [공식 스킬 레포](https://github.com/anthropics/skills) 19개와, 업스트림 레포 11곳에서 모은 1,812개짜리 집계본 [Universal AI Skills Library](https://github.com/onfire7777/universal-ai-skills-library). 모든 스킬이 같은 파이프라인을 탔다.

1. **린트**: frontmatter 파싱, name·description 존재, 깨진 상대 링크 없음.
2. **인젝션 스캔**: 지시 덮어쓰기, 자격증명 읽기, 권한 상승, 숨은 텍스트에 대한 정규식 블록리스트. 안전 증명이 아니라 블록리스트다.
3. **제약 추출**: LLM이 SKILL.md를 읽고 실행 가능한 지시 하나하나를 타입 있는 레코드로 바꾼다. subject, directive(require / forbid / prefer / avoid), object, scope, 그리고 원문 줄. 인용할 줄이 없는 제약은 버린다.
4. **쌍 비교**: 같은 subject에 반대 극성, scope가 겹치면 충돌 후보. 텍스트만으로 못 정하면 `conflict`가 아니라 `needs_review`.
5. **LLM judge**: 열린 쌍을 추출기와 다른 벤더의 모델이 원문 줄로 다시 읽는다.
6. **복종 테스트**: judge가 진짜 충돌이라 한 쌍은 두 스킬을 에이전트에 같이 넣고 그 규칙이 걸리는 태스크를 줘서 어느 쪽을 따르는지 기록한다.

외부 API 비용은 전체 **$15.75**. 추출 $6.23(gpt-6-luna, 손 라벨 세트에서 충돌 정밀도 1.0을 유지한 가장 싼 모델), judge $9.36(claude-sonnet-5.5), 태스크 생성 $0.16. 복종 테스트와 분류는 Claude Code 세션 안에서 돌렸다. 저자에 대해 한 줄: 파이프라인 설계와 판단은 내가 했고, 코드의 대부분과 실험 실행은 Claude Code가 했다. 이 글에서 "내가 읽었다"는 사람이 읽었다는 뜻이다. 코드와 숫자: [hyunlord/skillfetch](https://github.com/hyunlord/skillfetch).

## 1. 다섯 중 하나만 라이선스를 밝힌다

1,831개 중 377개(20.6%)만 자기 폴더나 복사해 온 업스트림 레포에 라이선스가 있다. 나머지는 아무 표시가 없다. 저작권법에서 표시 없음은 모든 권리 보유다. GitHub에서 읽을 수는 있지만, 인덱스에 담아 재배포할 수는 없다.

| 라이선스 상태 | 스킬 수 | 비율 |
| --- | --- | --- |
| 명시 (permissive 367, proprietary 10) | 377 | 20.6% |
| 업스트림 레포는 찾았지만 LICENSE 파일 없음 | 824 | 45.0% |
| 업스트림 불명 | 630 | 34.4% |

"업스트림은 있는데 라이선스 없음" 824개 중 822개가 `ComposioHQ/awesome-claude-skills` 한 곳에서 왔다. 레포 레벨 LICENSE가 없다. 이걸 다시 모은 라이브러리는 MIT지만, 집계 레포의 MIT 딱지가 다른 곳에서 복사한 파일에 라이선스를 부여하지는 못한다. 특정 프로젝트의 문제가 아니라 생태계 전체가 지금 이렇게 돌아가고 있고, 대부분의 메인테이너가 생각해본 적 없는 문제일 것이다. Anthropic 공식 레포도 섞여 있다. 19개 중 4개(docx, pdf, pptx, xlsx)는 all rights reserved고 1개는 라이선스 파일이 없다.

법적 판단이 아니라 표시 유무의 집계다. 하지만 스킬 본문을 재배포하는 "스킬 레지스트리"는 재고의 약 80%를 허가 없이 배포하고 있다는 뜻이다. 내 도구에 미친 영향은 명확했다. 인덱스에는 메타데이터와 콘텐츠 해시만 담고, 본문은 사용 시점에 원본 레포에서 가져와야 한다.

## 2. 107개는 기본 위생에서 탈락, 216개는 실행 스크립트 동봉

82개가 린트, 25개가 인젝션 스캔에서 탈락해 1,724개가 인덱스에 들어갔다. 린트 탈락은 대부분 깨진 링크다. 폴더에 없는 `references/auth.md`를 가리키거나, 스킬 바깥 파일을 가리킨다. 스캔 쪽이 더 흥미롭다.

| 스캔 규칙 | 건수 | 잡는 것 |
| --- | --- | --- |
| `privilege.dangerous-flag` | 23 | `--dangerously-skip-permissions`, `--no-sandbox` |
| `exfil.secret-env` | 7 | `$API_KEY`, `$TOKEN`, `$SECRET`의 echo나 전송 |
| `hidden.html-comment-instruction` | 7 | `<!-- -->` 안의 에이전트 지시 |
| `exfil.ssh-keys` | 5 | `~/.ssh` 읽기·복사 |
| `privilege.disable-sandbox` | 3 | "sandbox 비활성화/우회" |
| `exfil.cloud-credentials` | 3 | `~/.aws`, `~/.kube`, `~/.config/gcloud` |
| `hidden.invisible-chars` | 3 | 본문의 zero-width 문자 |
| `override.ignore-previous` | 1 | "ignore previous instructions" |
| `exfil.dotenv` | 1 | `.env` cat이나 업로드 |

직접 확인한 건들은 공격이 아니었다. 하나는 Anthropic의 API 가이드로, "ignore what the user said" 같은 프롬프트를 쓰지 말라고 조언하면서 그 문구를 인용했다가 걸렸다. 다른 하나는 headless Chrome에 `--no-sandbox`를 넘기는 E2E 테스트 스킬이었다. 이게 정확히 문제다. 정규식은 튜토리얼과 익스플로잇을 구분하지 못하고, 그 파일을 컨텍스트에 막 로드한 에이전트도 마찬가지다. 이런 스캔은 "볼 곳을 알려주는" 게이트로는 쓸 수 있지만 판결로는 못 쓴다. 25개를 전부 읽지는 않았으니 악성이 없다고는 못 하고, 패턴 매칭만으로는 그걸 알 수 없다고만 말할 수 있다.

별도로 216개는 에이전트가 실행할 셸·파이썬 스크립트를 동봉한다. 그 자체는 문제가 아니지만, 신뢰의 질문이 "이 텍스트가 에이전트에게 뭘 시키나"에서 "에이전트가 이 코드를 돌리면 무슨 일이 나나"로 바뀐다. 어떤 SKILL.md 린터도 답하지 않는 질문이다.

## 3. 스킬은 정면으로 모순되지 않는다. 서로를 좁힐 뿐이다.

예상 못 한 결과다. 파이프라인은 "기능 단위로 스쿼시해라" vs "절대 스쿼시하지 마라" 같은 쌍을 잡으려고 만들었다. 1,722개 스킬에서 뽑은 29,880개 제약에서 규칙이 충돌로 판정한 건 **2쌍**. 둘 다 읽었고, 둘 다 오탐이다.

```
CONFLICT  darwin ⟷ thinking-ooda
  darwin:        "Observe before acting."
  thinking-ooda: "Observe again after acting."
```

이건 OODA 루프지 모순이 아니다. 다른 하나는 "보안 발견은 상세히" vs "autorun 모드에서는 장황한 설명 생략". 상황이 다르다. 그러니 공개 스킬 1,700개에서 텍스트 정면 충돌의 정직한 숫자는 0이다.

규칙이 대신 찾은 건 판정 못 한 쌍 2,011개다. tension 137, `needs_review` 1,874. 이 전부를 다른 모델이 원문 줄로 다시 읽게 했다.

| judge 판정 | 쌍 | 비율 |
| --- | --- | --- |
| Independent (같은 주제, 양립) | 1,666 | 82.8% |
| Situational (다른 상황에서 각각 맞음) | 191 | 9.5% |
| Conflict | 90 | 4.5% |
| Carve-out (한쪽이 다른 쪽을 좁힘) | 57 | 2.8% |
| 오류·불분명 | 7 | 0.3% |

규칙에 수상해 보였던 쌍 다섯 중 넷은 문제없다. judge가 conflict라 한 90개도 대부분 "항상 물어보고 해라" vs "팀이 정해지면 다시 묻지 마라" 형태다. 한 규칙이 다른 규칙에 예외를 파는 것. judge는 이걸 과대 판정하는 경향이 있다. 손 라벨 세트에서 알려진 carve-out 7개 중 6개를 conflict라 했으니 90은 상한이다.

전체를 관통하는 패턴: 스킬 작성자들은 **무엇을** 할지를 다투지 않는다. **언제**와 **얼마나**를 다투어야 한다고 쓰고 있다. "응답은 짧게" vs "보안 발견은 철저히". "중요한 단계는 전부 로깅" vs "테스트 코드 안에서는 로깅 금지". 스킬의 버그가 아니다. 에이전트가 알아서 조율해야 하는 종류의 것이고, 질문은 실제로 그렇게 하나다.

## 4. 두 스킬이 갈릴 때 에이전트는 동전을 던지지 않는다. 매번 한쪽을 고른다.

judge가 conflict이면서 "함께 따르기 어렵다"고 본 쌍 26개를 골랐다. 쌍마다 다투는 규칙이 걸리는 태스크를 하나 써서, 두 스킬 본문을 다 넣고 우선순위 힌트 없이 새 에이전트 세션에서 5번 돌렸다. 순서는 바꿔가며(홀수 회차 A 먼저, 짝수 B 먼저), 각 출력을 A 따름 / B 따름 / 둘 다 / 둘 다 아님으로 분류했다.

| 5회 결과 | 쌍 수 |
| --- | --- |
| 5번 다 같은 한 스킬을 따름 | 17 |
| 5번 다 같은 비스킬 결과 (둘 다 / 둘 다 아님) | 2 |
| 섞임: 어떤 회차는 A, 어떤 회차는 B | 4 |
| 그 외 혼합 | 3 |

불확정적인 쌍은 26개 중 4개뿐이다. 17개에서 에이전트는 5번 중 5번 같은 한 스킬을 따랐다. 어느 스킬을 먼저 넣었는지는 상관이 없었다. 한쪽만 따른 경우 먼저 넣은 게 51번, 나중에 넣은 게 53번.

그러니 실패 양상은 랜덤이 아니다. **안정적이고 보이지 않는 우선순위**다. `tdd`와 `warden`을 깔았으면 둘이 갈리는 모든 태스크에서 한쪽이 이기고, 세션 어디에도 어느 쪽이 왜 이겼는지 나오지 않는다. 나중에 "에이전트가 왜 테스트를 먼저 안 쓰지?" 싶으면, 그 답은 3주 전에 깔은 스킬의 한 줄이다.

중요한 경고 둘. 첫째, 하네스 문구가 결과를 바꾼다. 버린 배치에서 "이 답변 하나로 끝내라"는 문구는 "멈추고 사용자에게 물어보라"는 규칙을 전부 지게 했다. 멈추기 vs 진행하기 쌍이 가장 취약하다. 둘째, 130개 출력을 한 사람이 분류했다. 소수점 있는 숫자를 말하기 전에 두 번째 평가자가 필요하다.

**스킬에 순서를 줄 수 없다.** 뻔한 해법은 어느 스킬이 이기는지 에이전트에게 알려주는 것이다. 같은 26쌍에 세 가지 방법을 써봤다. A를 승자로 지정해 5번, B를 승자로 지정해 5번, 방법마다 260번, 하네스와 분류는 같다.

| 승자를 알린 방법 | 지정한 승자를 따른 실행 |
| --- | --- |
| 스킬 앞 헤더: "Skills are listed in precedence order. If two instructions disagree, follow the earlier one." (`load_skills`가 넣는 문구) | 43% (112/260) |
| 승자를 지명하고 충돌하는 두 줄을 인용한 블록 | 56% (145/260) |
| 지는 스킬의 충돌 줄을 `<!-- overridden by <winner>: "<line>" -->`로 치환 | 46% (120/260) |

위의 130번까지 합쳐 910번이다. 쌍별 표는 [numbers.md](numbers.md) §8–§10.

## 도구가 틀리는 것

파이프라인은 정밀도를 재현율보다 우선하도록 튜닝되었고, 그 비용이 숫자에 보인다.

- **재현율은 측정되지 않았다.** 공개 스킬 1,700개를 충돌 기준으로 손 라벨한 사람은 없다. 도구가 거짓말을 거의 안 한다고는 말할 수 있지만, 얼마나 놓치는지는 모른다. 기본 모드는 object가 없는 전면 규칙("이모지 금지")을 일부러 `needs_review`로 내린다. 실제 스킬에서 모든 오탐이 거기서 나왔기 때문이다. 내 손 라벨 테스트 세트에서는 그게 진짜 충돌 19개 중 8개를 숨긴다.
- **judge는 한쪽으로 기울어진다.** 알려진 carve-out 7개 중 6개를 conflict라 했다. 90은 상한이다.
- **추출 프롬프트 6버전, 테스트 세트 하나.** 손으로 쓴 스킬 41개에 맞춰 추출 스키마를 여섯 번 고쳤고 거기서 1.0이 나왔다. 그 다음 실제 스킬 219개에서는 충돌 24개를 냈고 전부 오탐이었다. 독립 표본 두 번을 더 거쳤고 지금은 0~2개다. 튜닝한 세트에서 만점은 holdout이 동의하기 전까지 아무 의미가 없다.
- **오탐 2개가 산출물에 그대로 들어 있다.** 고치는 대신 README에 그렇다고 적었다.
- **anti-pattern 테이블이 추출기를 속인다.** "❌ Don't" 테이블의 행이 지시로 읽힌다. 이슈로 열려 있다.
- **추출은 의미 작업이라 모델이 필요하다.** gpt-6-luna로 스킬당 약 $0.003(최종 실행 1,764개에 $4.82). 더 싼 모델은 오탐을 냈고, 15배 비싼 모델은 점수가 더 낮았다. 모델 크기보다 프롬프트 구조가 중요했다.

## 써보기, 그리고 다음

스캐너는 로컬 스킬 디렉터리 어디에나 돌아가고, 모든 판정에 원인이 된 원문 줄 두 개를 같이 찍는다. 공개 스킬의 사본은 공개 인덱스에서 바로 분석되므로 모델이나 API 키가 필요 없다.

```
uvx --from git+https://github.com/hyunlord/skillfetch skillfetch sync
uvx --from git+https://github.com/hyunlord/skillfetch skillfetch scan ~/.claude/skills
uvx --from git+https://github.com/hyunlord/skillfetch skillfetch scan ~/.claude/skills --fail-on conflict   # CI용
```

원래 만들려던 건 나머지 반이다. 스킬의 80%는 재배포할 수 없고, 대부분은 같이 써도 괜찮고, 안 괜찮은 것들은 조용한 우선순위로 해소된다는 걸 알고 나니, 원하는 건 **스킬을 아예 설치하지 않는** 에이전트다. 태스크마다 검증된 인덱스를 검색해 작은 세트를 골라서, 위의 긴장 관계를 검사하고, 본문은 원본 레포에서 해시 검증해 가져오고, 태스크가 끝나면 버린다. 그 MCP 서버의 초기 버전이 레포에 있다. `search_skills`, `resolve_set`, `load_skills`, Claude Code에서 엔드투엔드로 동작한다. 인덱스에는 메타데이터·제약·해시만 있고 본문은 없다.

<!-- 1단계 비용: 턴, 토큰, 정확성 (블라인드 결과 확인 후 기입) -->

스킬을 관리한다면 LICENSE 파일을 넣어라. 레지스트리를 관리한다면 그걸 보여줘라. 서로 안 맞는 것 같은 스킬 한 쌍이 있으면 스캐너를 돌려서 결과를 이슈로 열어줘라. 뭐를 잡는지보다 뭐를 놓치는지가 더 알고 싶다.
